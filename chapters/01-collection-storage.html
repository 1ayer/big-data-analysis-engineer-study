데이터 수집·저장과 법적 경계

수집 가능성과 이용 가능성은 다르다. 출처·목적·품질·법적 근거를 확인하고 사용 방식에 맞는 저장 구조를 선택한다.

공식 범위 · 데이터 수집 및 저장 계획

수집 타당성부터 저장·보안·운영까지

데이터 유형과 원천, 수집 방식, 품질, 개인정보보호, 적재 파이프라인과 분산 처리를 하나의 흐름으로 다룬다.

이 단원을 마치면

  • 원천과 지연시간 요구에 맞춰 배치·스트림·응용 프로그래밍 인터페이스(API)·로그·크롤링을 구분한다.
  • 데이터 품질을 정확성·완전성·유효성·일관성·적시성·유일성으로 진단한다.
  • 개인정보와 가명정보, 수집·이용 근거와 가명·익명처리의 차이를 구분한다.
  • 추출·변환·적재(ETL)와 추출·적재·변환(ELT), 웨어하우스·레이크·관계형·NoSQL 저장소를 목적에 맞춰 고른다.
  • 하둡 분산 파일 시스템(HDFS)과 MapReduce의 역할, 장점과 한계를 설명한다.

핵심 1 · 수집 계획

목적과 기준시점이 원천·주기·방법을 결정한다

  1. 목적어떤 결정에 필요한가
  2. 원천누가 어떻게 생성했나
  3. 범위대상·기간·필드·표본
  4. 주기배치·근실시간·실시간
  5. 근거권한·계약·법적 근거
  6. 통제품질·보안·비용·복구

1. 내부·외부 원천의 생성 과정을 먼저 본다

원천수집 방식핵심 점검
업무 DB쿼리, 변경 데이터 캡처, 덤프운영 부하·기준시점·삭제와 갱신
애플리케이션 로그파일 수집, 메시지 큐, 이벤트 스트림이벤트 정의·중복·순서·시간대
응용 프로그래밍 인터페이스(API)인증된 요청과 응답 적재약관·권한·페이지네이션·속도 제한·재시도
웹크롤링·파싱robots.txt·약관·저작권·개인정보·요청 부하
센서·장비게이트웨이·스트림교정·결측·노이즈·단위·장치 시각
외부 파일다운로드·전송·공유라이선스·버전·갱신주기·무결성

같은 필드명이라도 생성 규칙이 바뀌면 의미가 달라진다. 수집 명세에는 원천 소유자, 추출 조건, 단위·코드, 기준시각과 시간대, 갱신·삭제 규칙, 실패 재처리, 보존기간과 사용조건을 남긴다.

2. 배치와 스트림은 처리 시점의 선택이다

구분배치스트림
처리모인 데이터를 일정 주기로 처리연속 이벤트를 도착에 가깝게 처리
적합일일 집계, 대량 재처리, 정기 보고이상 탐지, 실시간 추천, 상태 감시
설계 쟁점처리 창·의존성·재실행이벤트 시간·지연·순서·중복·상태
비용단순하고 처리 효율이 높기 쉬움낮은 지연 대신 운영 복잡성이 큼

실시간은 무조건 우월하지 않다. 의사결정이 하루 한 번이면 배치가 더 단순하고 재현 가능할 수 있다. 스트림에서도 장애 재처리 때문에 같은 이벤트가 다시 올 수 있으므로, 동일 요청을 반복해도 결과가 불필요하게 중복되지 않는 멱등성과 이벤트 식별자를 설계한다.

3. 크롤링 가능성과 이용 정당성은 분리한다

응용 프로그래밍 인터페이스(application programming interface, API)는 프로그램끼리 정해진 방식으로 요청과 응답을 주고받는 접점이다. 국제 인터넷 표준 문서(Request for Comments, RFC) 9309의 robots.txt는 서비스 소유자가 크롤러의 통합 자원 식별자(Uniform Resource Identifier, URI) 접근 규칙을 게시하는 표준이다. RFC 자체도 이 규칙이 접근 권한 부여가 아니라고 명시한다. 즉 robots.txt가 허용하더라도 약관·저작권·개인정보·계약과 요청 부하를 별도로 검토해야 하고, 금지된 경로를 기술적으로 열 수 있다고 수집해서는 안 된다.

  • 식별 가능한 User-Agent와 연락처, 합리적인 요청 간격을 둔다.
  • 필요한 최소 필드와 기간만 수집하고 원문 재배포 권한을 확인한다.
  • 응답코드·재시도·중단 기준과 원천 변경 감지를 기록한다.
  • 공식 API가 있다면 구조·정책·부하 관리가 명확한 API를 우선 검토한다.

핵심 2 · 품질과 데이터 계보

좋은 데이터는 목적에 맞고 설명 가능하다

차원질문검사 예
정확성현실의 참값을 올바르게 나타내는가?검증 원천과 대조, 측정기 교정
완전성필요한 값과 레코드가 빠지지 않았는가?필수값 결측률, 기간별 건수
유효성형식·범위·도메인 규칙을 만족하는가?날짜 형식, 허용 코드, 값 범위
일관성시스템·필드·기간 사이 의미가 맞는가?합계 대조, 코드 매핑, 단위 확인
적시성필요한 시점에 최신 상태인가?원천 발생과 적재 시각의 지연
유일성같은 실체가 불필요하게 중복되지 않았는가?업무키 중복률, 중복 이벤트 ID

정확성과 유효성은 다르다. 나이 150은 범위 규칙으로 유효하지 않다고 판정할 수 있지만, 형식상 유효한 나이 35가 실제로 정확한지는 외부 근거가 필요하다. 결측 0%도 기본값 0으로 잘못 채웠다면 품질이 높지 않다.

메타데이터·계보·무결성은 서로 다른 질문에 답한다

요소답하는 질문예
업무 메타데이터이 값은 업무에서 무엇을 뜻하나?이탈의 정의, 코드 사전, 소유자
기술 메타데이터어떤 형식과 위치에 있나?스키마, 자료형, 테이블·파일 경로
운영 메타데이터언제 어떤 작업이 수행됐나?적재 시각, 행 수, 작업 상태
데이터 계보어디서 와서 어떤 변환을 거쳤나?원천 열 → 정제 → 특징 → 보고서
체크섬전송·보관 중 바이트가 바뀌었나?동일 파일의 256비트 보안 해시 알고리즘(SHA-256) 비교

체크섬 일치는 파일이 전송 중 변하지 않았다는 근거일 뿐 내용이 정확하거나 안전하다는 뜻은 아니다. 데이터 계보는 오류 원천 추적, 재현, 영향 분석과 규제 대응을 돕는다.

핵심 3 · 개인정보보호

동의 여부 하나가 아니라 목적·근거·최소성·보호조치를 본다

적용 기준

아래는 2026년 8월 13일 현재 국가법령정보센터의 개인정보 보호법과 개인정보보호위원회 가이드라인을 대조한 학습용 요약이다. 실제 수집·결합·제공에는 최신 법령, 하위 규정, 처리 맥락과 조직의 법무·개인정보 담당자 검토가 필요하다.

1. 개인정보와 가명정보

개인정보 보호법 제2조의 개인정보는 살아 있는 개인에 관한 정보로서 그 자체로 개인을 알아볼 수 있는 정보뿐 아니라, 다른 정보와 쉽게 결합해 알아볼 수 있는 정보와 가명처리한 정보도 포함한다. 쉽게 결합할 수 있는지는 시간·비용·기술 등을 합리적으로 고려한다.

가명처리는 추가정보 없이는 특정 개인을 알아볼 수 없도록 일부를 삭제하거나 대체하는 등 처리하는 것이다. 가명정보는 개인정보의 한 범주이므로 “이름을 지웠으니 개인정보가 아니다”라고 단정하면 틀리다.

2. 수집·이용은 동의만이 유일한 근거가 아니다

제15조는 동의를 포함한 법정 근거 중 하나가 있을 때 개인정보를 수집할 수 있고, 그 수집 목적 범위에서 이용할 수 있도록 한다. 법률상 의무 준수, 공공기관의 소관 업무, 계약 체결·이행, 급박한 생명·신체·재산 이익, 일정 요건을 갖춘 정당한 이익 등도 조문상 근거가 될 수 있다.

따라서 시험에서 “개인정보는 오직 동의가 있어야만 처리 가능하다”는 절대 표현은 틀릴 가능성이 높다. 반대로 근거 하나가 있다고 무제한 처리할 수 있는 것도 아니다. 목적 명확성, 필요한 최소 수집, 안전조치, 보유기간과 정보주체 권리 등 전체 원칙을 함께 지킨다.

3. 가명정보 특례의 조건

  • 제28조의2에 따라 통계작성, 과학적 연구, 공익적 기록보존 등을 위해 정보주체 동의 없이 가명정보를 처리할 수 있다.
  • 이 목적으로 제3자에게 제공할 때 특정 개인을 알아보기 위해 사용할 수 있는 정보를 포함해서는 안 된다.
  • 서로 다른 개인정보처리자 간 가명정보 결합은 지정된 전문기관이 수행한다.
  • 추가정보는 가명정보와 분리 보관하고 기술적·관리적·물리적 안전조치와 처리기록을 갖춘다.
  • 특정 개인을 알아보기 위한 처리를 해서는 안 되며, 개인을 알아볼 수 있는 정보가 생성되면 처리를 중지하고 회수·파기해야 한다.

법적 경계 · 가명처리는 위험을 낮추는 통제다

가명처리를 했다고 모든 의무가 사라지는 것은 아니다. 추가정보 분리와 접근통제로 재식별 위험을 낮추는 방식이며, 결합 가능한 외부 데이터가 달라지면 위험도 다시 검토해야 한다.

4. 기법의 이름보다 남은 식별 위험을 평가한다

기법예남는 위험
삭제·마스킹이름 삭제, 전화번호 일부 가림나머지 속성의 조합으로 알아볼 수 있음
대체고객번호를 임의 식별자로 교체대응표가 노출되거나 다른 자료와 연결될 수 있음
일반화·범주화나이를 연령대로, 주소를 시·도로 변환희귀한 속성 조합은 여전히 두드러질 수 있음
집계·노이즈소규모 셀을 합치거나 통계값을 교란유용성과 정확도가 줄고 반복 공개로 정보가 누적될 수 있음

가명·익명 여부는 “마스킹을 했다” 같은 기법명 하나로 정해지지 않는다. 이용 목적, 데이터 상세도, 외부에서 결합 가능한 정보, 접근 권한과 시간·비용·기술을 함께 보고 식별 가능성을 판단한다. 개인정보보호위원회의 2026년 안내서는 준비 → 위험성 검토 → 가명처리 → 적정성 검토 → 안전한 관리의 순환을 강조한다.

사진·영상·음성·자연어 같은 비정형 데이터에는 얼굴·음성뿐 아니라 배경, 위치, 문신, 문서 속 이름처럼 여러 식별 단서가 함께 들어갈 수 있다. 자동 탐지 결과를 그대로 믿지 말고 샘플 검수와 잔여 위험 점검을 더한다.

핵심 4 · 적재 파이프라인

추출·변환·적재(ETL)와 추출·적재·변환(ELT)은 변환 위치가 다르다

ETL(extract, transform, load)은 적재 전에 변환하고, ELT(extract, load, transform)는 먼저 적재한 뒤 대상 플랫폼에서 변환한다.

구분ETLELT
순서추출 → 변환 → 적재추출 → 적재 → 변환
변환 장소적재 전 별도 처리 계층대상 저장·분석 플랫폼 내부
장점정제·표준화된 데이터만 대상에 적재원본 보존과 다양한 후속 변환에 유연
주의요구 변경 때 원천 재처리가 어려울 수 있음민감 원본의 접근통제·비용·중복 변환 관리

ETL과 ELT 중 하나가 항상 우월하지 않다. 대상 플랫폼의 계산 능력, 원본 보존 필요, 데이터 민감도, 변환 재현성, 비용과 지연시간에 따라 고른다.

  1. Extract원천을 일관된 기준시점과 증분 규칙으로 읽는다.
  2. Validate스키마·건수·필수값·범위·중복·무결성을 검사한다.
  3. Transform정제·통합·코드·단위·파생변수 규칙을 버전 관리한다.
  4. Load원자적 교체·중복 방지·실패 복구를 고려해 적재한다.
  5. Observe지연·실패·품질·비용·계보를 감시하고 경보를 연결한다.

재처리 가능성을 확보하려면 원천 스냅샷이나 변경 이력, 코드와 설정 버전, 실행 시각·입력·출력 건수, 품질 결과를 남긴다. 비밀키나 직접식별자를 로그에 남기는 것은 추적성이 아니라 노출 위험이다.

핵심 5 · 저장 기술

데이터 모양보다 읽기·쓰기·일관성 요구로 고른다

저장 구조강점적합한 접근주의
관계형 DB명확한 스키마·제약·트랜잭션·조인정합성이 중요한 업무 처리비정형·초대규모 수평 확장은 설계 필요
데이터 웨어하우스통합·정제된 분석용 모델과 SQL일관된 지표·보고·OLAP모델링·적재 비용, 원천 유연성
데이터 레이크다양한 원본·가공 데이터를 유연하게 보존탐색·재처리·대규모 분석카탈로그·품질·권한 없으면 찾기 어려움
키-값키 기반 단순·빠른 조회와 확장세션·캐시·프로필 조회복잡 질의·관계 표현이 제한적
문서형중첩 문서와 유연한 스키마콘텐츠·상품·이벤트 문서스키마 규율과 조인 방식 검토
열 계열희소하고 넓은 데이터를 분산 저장대규모 시계열·이벤트 조회접근 패턴 중심 설계 필요
그래프 DB노드·관계 순회와 경로 질의추천·사기 네트워크·지식 그래프단순 집계에는 불필요할 수 있음

SQL(Structured Query Language)은 관계형 데이터를 정의·조회·변경하는 질의 언어다. NoSQL은 “SQL을 절대 쓸 수 없다”는 뜻보다 관계형 모델 외의 다양한 분산 저장 모델을 묶는 실무적 범주로 이해한다. OLAP(online analytical processing)은 여러 관점에서 집계·비교하는 분석 처리를 가리킨다. 제품명보다 질의 형태, 쓰기량, 일관성, 지연시간, 확장과 운영 역량을 먼저 본다.

웨어하우스와 레이크의 경계

웨어하우스는 주제 중심으로 통합·정제한 데이터를 일관된 분석에 제공하고, 레이크는 원본을 포함한 다양한 형식의 데이터를 유연하게 보존한다. schema-on-write는 쓰기 전에 구조를 엄격히 맞추는 경향, schema-on-read는 읽을 때 목적에 맞게 구조를 적용하는 경향을 설명한다. 실제 플랫폼은 두 방식을 섞을 수 있으므로 절대 구분으로 외우지 않는다.

저장 계획에 함께 적을 운영 항목

  • 파티셔닝: 자주 거르는 키와 데이터 분포를 고려하고 쏠림을 감시한다.
  • 보존·파기: 목적과 법적 근거에 맞는 기간, 삭제 전파와 검증 절차를 둔다.
  • 백업·복구: 복구 시점 목표와 복구 시간 목표를 정하고 실제 복구를 시험한다.
  • 접근통제: 최소권한, 인증·권한분리, 전송·저장 암호화와 감사기록을 적용한다.
  • 카탈로그: 소유자·스키마·품질·민감도·계보와 사용조건을 검색 가능하게 한다.

핵심 6 · 분산 저장과 처리

하둡 분산 파일 시스템(HDFS)은 블록으로 저장하고 MapReduce는 데이터 가까이 계산한다

1. 하둡 분산 파일 시스템(Hadoop Distributed File System, HDFS)의 역할 분리

구성역할핵심 통신
NameNode파일시스템 네임스페이스와 블록 매핑·복제 결정 관리DataNode의 Heartbeat·Blockreport 수신
DataNode실제 블록 저장, 읽기·쓰기와 블록 생성·삭제·복제 수행클라이언트 데이터 I/O와 상태 보고
블록·복제파일을 블록으로 나누고 여러 DataNode에 복제노드 장애에도 읽기·복구 가능성 향상

HDFS는 대용량 파일의 스트리밍 접근과 높은 처리량, 한 번 쓰고 여러 번 읽는 패턴을 중심으로 설계됐다. 많은 작은 파일, 매우 낮은 지연의 임의 읽기, 잦은 위치 수정에는 적합하지 않을 수 있다. 복제는 가용성을 높이지만 백업·논리 오류 방지와 완전히 같은 것은 아니다.

2. MapReduce(map과 reduce)의 데이터 흐름

  1. 입력 분할입력을 여러 조각으로 나눠 병렬 작업을 만든다.
  2. Map입력 키·값에서 중간 키·값을 생성한다.
  3. Shuffle·Sort같은 중간 키의 값을 모아 정렬·전달한다.
  4. Reduce키별 값 묶음을 집계·결합해 출력을 만든다.
  5. 복구프레임워크가 작업을 추적하고 실패 작업을 재실행한다.

단어 수 세기에서 Map은 각 단어에 (단어, 1)을 내고, Shuffle·Sort가 같은 단어를 모으며, Reduce가 1들을 합친다. 데이터를 저장한 노드 가까이 계산을 배치하는 데이터 지역성은 네트워크 전송을 줄인다. 반복 알고리즘은 단계마다 디스크 I/O가 커질 수 있어 모든 분석에 최선은 아니다.

9분 · 답을 보지 않고 떠올리기

먼저 답해 보고 펼쳐 보세요

1. 수집 명세에 들어갈 핵심 시간 정보는?

원천 발생·기준시각과 시간대, 수집·갱신 주기, 지연 허용치, 보존기간이다.

2. 배치와 스트림의 핵심 차이는?

배치는 모인 데이터를 주기적으로 처리하고, 스트림은 연속 이벤트를 도착에 가깝게 처리한다.

3. 멱등성이 중요한 이유는?

재시도나 중복 이벤트가 생겨도 같은 처리를 반복해 불필요한 중복 결과를 만들지 않게 하기 위해서다.

4. robots.txt가 허용하면 법적 이용 권한도 생기는가?

아니다. RFC 9309도 robots 규칙은 접근 권한 부여가 아니라고 하며 약관·저작권·개인정보 등을 별도로 검토한다.

5. 정확성과 유효성의 차이는?

유효성은 형식·범위 규칙 준수이고, 정확성은 현실의 참값을 올바르게 나타내는지다.

6. 데이터 계보가 답하는 질문은?

데이터가 어디서 와서 어떤 변환을 거쳐 현재 결과가 됐는지다.

7. 체크섬 일치가 보장하지 않는 것은?

내용의 정확성·적법성·안전성은 보장하지 않고 바이트 변경 여부만 확인한다.

8. 가명정보는 개인정보인가?

그렇다. 개인정보 보호법 제2조의 개인정보 정의에 포함된다.

9. 개인정보 수집·이용에서 동의는 유일한 근거인가?

아니다. 제15조가 정한 여러 법적 근거 중 하나다.

10. 동의 없이 가명정보를 처리할 수 있는 대표 목적은?

통계작성, 과학적 연구, 공익적 기록보존 등이다.

11. ETL과 ELT의 순서는?

ETL은 추출→변환→적재, ELT는 추출→적재→변환이다.

12. 웨어하우스와 레이크의 대표 차이는?

웨어하우스는 통합·정제된 분석 데이터와 일관된 지표에, 레이크는 다양한 원본·가공 데이터의 유연한 보존과 재처리에 무게를 둔다.

13. HDFS의 NameNode와 DataNode 역할은?

NameNode는 네임스페이스와 블록 메타데이터를 관리하고 DataNode는 실제 블록을 저장한다.

14. MapReduce의 세 핵심 처리 단계는?

Map, Shuffle·Sort, Reduce다.

15. 데이터 지역성의 이점은?

데이터 가까이에 계산을 배치해 대규모 네트워크 전송을 줄인다.

16. 이름을 삭제한 것만으로 익명정보라 단정할 수 없는 이유는?

다른 속성의 조합이나 외부 정보와의 결합으로 개인을 알아볼 가능성이 남을 수 있기 때문이다.

17. 가명처리의 위험성 검토에서 함께 볼 요소는?

이용 목적, 데이터 상세도와 희귀성, 결합 가능한 외부 정보, 접근 권한과 시간·비용·기술 등이다.

    2. DataNode
    3. Reducer
    4. System Orchestrator
    정답과 해설

    B. NameNode는 네임스페이스와 블록 메타데이터를 관리한다.

  14. HDFS에 특히 부적합할 가능성이 큰 작업은?

    1. 대용량 파일의 순차 스트리밍 읽기
    2. 한 번 쓴 대형 로그의 반복 분석
    3. 수많은 작은 파일을 매우 낮은 지연으로 자주 위치 수정
    4. 노드에 분산된 블록의 병렬 처리
    정답과 해설

    C. HDFS는 대용량 파일의 높은 처리량과 쓰기 한 번·읽기 여러 번 패턴에 무게를 둔다.

  15. MapReduce에서 같은 중간 키의 값들을 모아 Reducer로 보내는 단계는?

    1. Extract
    2. Shuffle·Sort
    3. Schema-on-write
    4. Heartbeat
    정답과 해설

    B. Map 출력은 키에 따라 분배·정렬돼 Reduce 입력으로 묶인다.

  16. 이름을 삭제하고 나이·희귀 직업·세부 지역을 그대로 공개했다. 가장 타당한 판단은?

    1. 이름이 없으므로 무조건 익명정보다.
    2. 속성 조합과 외부 정보로 알아볼 위험을 다시 평가해야 한다.
    3. 가명정보는 안전조치가 필요 없다.
    4. 희귀한 속성일수록 식별 위험이 줄어든다.
    정답과 해설

    B. 처리 기법의 이름이 아니라 남은 식별 가능성과 이용 환경을 함께 판단한다.

  17. 영상 데이터의 가명처리에서 특히 적절한 점검은?

    1. 얼굴만 흐리면 다른 검토는 필요 없다.
    2. 배경의 주소·차량번호·문신 같은 간접 식별 단서도 확인한다.
    3. 파일명을 바꾸면 영상 내용도 가명처리된다.
    4. 자동 탐지 결과는 샘플 검수 없이 항상 완전하다.
    정답과 해설

    B. 비정형 데이터에는 다양한 직접·간접 식별 단서가 함께 있어 잔여 위험을 검수해야 한다.
